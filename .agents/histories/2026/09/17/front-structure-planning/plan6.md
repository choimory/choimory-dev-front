# 개요

- `plan5.md`와 `task5.md`를 통해 플랫폼 홈과 blog 화면의 비로그인/로그인 분기 구조를 만들었다.
- 이번 단계에서는 plan5 이후 남은 작업을 정리한다.
- 현재 구현은 눈에 크게 드러나는 디자인 변경보다, 실제 로그인 연동 전에 화면 구조를 나눌 수 있는 기반 작업에 가깝다.

---

# plan5 이후 현재 상태

- 플랫폼 홈에 `authStatus: 'guest' | 'member'` 구조가 추가되었다.
- blog 화면에 `authStatus: 'guest' | 'member'` 구조가 추가되었다.
- 비로그인 상태에서는 소개와 로그인/회원가입 CTA 중심 화면을 보여준다.
- 로그인 상태에서는 회원용 피드 또는 활동 요약 화면을 보여줄 수 있다.
- 현재 임시 데이터의 기본값은 `guest`이므로 화면에서 큰 변화가 덜 느껴질 수 있다.
- `authStatus`를 `member`로 바꾸면 플랫폼 홈에서는 오늘 요약/최근 활동 피드가 보이고, blog에서는 글쓰기/필터/작성 박스가 포함된 회원 피드가 보인다.
- 서비스 목록은 블로그, 메모, 피드, 가계부, 일정 중심으로 정리되었다.

# 남은 작업

## 비로그인 랜딩 화면 고도화

현재 비로그인 화면은 구조상 분리되었지만, 아직 소개 카드 수준에 가깝다.

남은 작업:

- 플랫폼 홈 `/` 비로그인 화면을 `choimory.dev` 서비스 허브처럼 보이게 다듬기
- 단순 카드보다 서비스의 성격과 진입점을 더 잘 보여주는 랜딩 구조 만들기
- blog 비로그인 화면을 공개 피드와 가입 유도 흐름이 자연스럽게 이어지도록 정리하기
- 비로그인 사용자가 둘러볼 수 있는 영역과 로그인해야 가능한 영역을 화면에서 명확히 구분하기

## 로그인 상태 화면 확인용 전환 장치

현재는 개발 중 회원 화면을 확인하려면 코드의 `authStatus` 값을 직접 바꿔야 한다.

남은 작업:

- 개발 중 `guest/member` 화면을 쉽게 확인할 수 있는 임시 전환 방식을 정하기
- URL query, mock session, 개발용 플래그 중 어떤 방식을 쓸지 결정하기
- 실제 인증 연동 전까지 화면 확인이 쉬운 구조 만들기

후보:

- `?auth=member` 같은 URL query 기반 전환
- mock session 데이터 기반 전환
- 개발 환경에서만 사용하는 임시 플래그

## 회원용 플랫폼 홈 다듬기

현재 회원용 플랫폼 홈은 오늘 요약과 최근 활동 피드의 뼈대만 있다.

남은 작업:

- 서비스별 요약을 더 구체화하기
- 자주 쓰는 서비스와 최근 사용 서비스를 구분할지 검토하기
- 알림 피드와 최근 활동 피드의 역할을 나누기
- 메모, 피드, 가계부, 일정 같은 서비스의 회원용 요약 데이터를 어떻게 보여줄지 정하기

## blog 회원 화면 UX 정리

현재 blog 회원 화면은 기존 피드 UI를 별도 컴포넌트로 분리한 상태다.

남은 작업:

- 하단 네비게이션 항목 확정하기
- 검색, 내 blog 홈, 글쓰기 진입을 어디에 둘지 정하기
- 현재 하단 항목인 피드, 인기, 작성, 홈을 유지할지 검토하기
- 상단 액션과 하단 툴바의 역할을 분리하기

고민 중인 항목:

- 플랫폼 홈
- blog 홈
- 내 blog 홈
- 검색
- 글쓰기

## 서비스별 라우트 확장

현재 실제 화면이 있는 라우트는 제한적이다.

현재 주요 라우트:

- `/`
- `/blog`
- `/login`
- `/signup`
- `/me`

아직 화면이 없는 서비스:

- 메모
- 피드
- 가계부
- 일정

남은 작업:

- `/memo` 라우트 뼈대 추가
- `/feed` 라우트 뼈대 추가
- `/account-book` 라우트 뼈대 추가
- `/schedule` 라우트 뼈대 추가
- 각 서비스의 첫 화면이 비로그인/로그인 상태에서 어떻게 달라질지 정하기

## 실제 인증 연동 전 준비

현재 `authStatus`는 각 ViewModel에 임시로 들어가 있다.

남은 작업:

- 실제 로그인 API를 붙이기 전, 프론트에서 세션 상태를 어디서 읽을지 정하기
- 각 ViewModel에 `authStatus`를 직접 넣는 방식을 계속 쓸지 검토하기
- 공통 session model 또는 provider가 필요한지 검토하기
- 상단바, 플랫폼 홈, blog 화면, 마이페이지가 같은 인증 상태를 바라보게 만들기

아직 제외할 실제 기능:

- 로그인 API 연동
- 회원가입 API 연동
- 소셜 로그인 OAuth 연동
- 세션 저장
- 마이페이지 저장
- 2차 인증
- 회원 탈퇴

# 1차 구현계획

## 구현 범위

1차 구현에서는 화면에서 변화가 잘 보이도록 비로그인 랜딩 고도화를 먼저 진행한다.

구현 범위:

- 플랫폼 홈 비로그인 랜딩 고도화
  - 현재 `GuestLandingSection`을 단순 소개 카드에서 서비스 허브형 랜딩 섹션으로 확장한다.
  - `choimory.dev`가 어떤 플랫폼인지 한눈에 보이도록 구성한다.
  - 로그인/회원가입 CTA는 유지한다.
  - 블로그, 메모, 피드, 가계부, 일정으로 이어지는 서비스 소개를 추가한다.
- blog 비로그인 화면 고도화
  - 소개 카드의 `choimory.dev / blog` 로고 구조는 유지한다.
  - 공개 게시글 미리보기와 로그인 유도 영역을 구분한다.
  - 비회원이 둘러볼 수 있는 영역과 로그인해야 가능한 영역을 이해할 수 있게 만든다.
- guest/member 전환 확인용 mock 구조 추가
  - 개발 중 `authStatus`를 코드에서 직접 바꾸지 않아도 확인할 수 있게 한다.
  - URL query 방식을 우선 사용한다.
  - 예시는 `/?auth=member`, `/blog?auth=member` 형태다.
  - 실제 인증 연동 전까지 화면 확인용으로만 사용한다.
- 구현 후 `task6.md`에 변경 사항을 작성한다.
- 검증은 `npx tsc --noEmit`, `npm run lint`, `npm run build` 기준으로 진행한다.

## 권장 구현 순서

1. 현재 구조 재확인
   - `PlatformHomeView`, `GuestLandingSection`, `BlogGuestSection`, 각 ViewModel 구조를 확인한다.
   - Next.js 16 기준으로 `searchParams` 처리 방식을 확인한다.
2. mock auth 상태 처리 추가
   - `/`와 `/blog` page에서 query를 읽어 `authStatus`를 결정한다.
   - `?auth=member`면 `member`, 그 외에는 `guest`로 처리한다.
   - 실제 인증 붙일 때 교체하기 쉽도록 작은 helper로 분리한다.
3. 플랫폼 홈 비로그인 랜딩 개선
   - `GuestLandingSection`을 서비스 허브형 구조로 확장한다.
   - 서비스별 진입 정보와 요약 리스트를 추가한다.
   - 앱 첫 화면 안에서 자연스럽게 보이도록 과한 마케팅 페이지 형태는 피한다.
4. blog 비로그인 화면 개선
   - 상단 소개 영역을 정리한다.
   - 공개 글 미리보기 섹션 타이틀을 추가한다.
   - 로그인해야 가능한 액션을 CTA로 분리한다.
5. 검증 및 문서화
   - 타입 검사, 린트, 빌드를 실행한다.
   - 구현 내용을 `task6.md`에 기록한다.

## 주의할 점

- 랜딩을 새 페이지처럼 과하게 키우면 현재 모바일 앱형 구조와 충돌할 수 있다.
- 카드 안에 카드를 중첩하지 않는다.
- mock auth 구조는 실제 인증 로직처럼 과설계하지 않는다.
- URL query 방식은 개발 확인용이라는 점을 코드와 문서에 명확히 남긴다.
- blog 상단의 `choimory.dev / blog` 로고 구조는 유지한다.
