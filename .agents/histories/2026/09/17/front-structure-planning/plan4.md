# plan4 해당사항 분석

`plan4`는 `plan3.md`, `task3.md` 이후 이어갈 화면 구성 작업이다.

현재 `task3.md` 기준으로는 `/community`가 `/blog`로 전환되었고, 플랫폼 홈은 `768px` 기준의 `choimory.dev` 메인, 검색바, 서비스 런처, 비회원 소개 섹션, 하단 툴바 구조까지 구현된 상태다.

다만 아직 다음 항목들은 구현되지 않았다.

- 사이트 로고
- 로그인 화면
- 회원가입 화면
- 마이페이지 화면
- 로그인/비로그인 사용자 기준의 플랫폼 홈 분기
- 로그인/비로그인 사용자 기준의 blog 화면 분기
- 플랫폼과 blog 각각의 하단 툴바 정책 정리
- README.md 최신화
- 타입 검사, 린트, 빌드 검증

`README.md`는 현재 실제 코드와 맞지 않는 부분이 있다.

- 실제 코드는 `/blog`, `features/blog`를 사용한다.
- README.md는 아직 `/community`, `features/community`를 설명한다.
- 따라서 다음 구현 전 또는 구현 초기에 README.md를 최신 구조 기준으로 갱신해야 한다.

# 규칙과 현재 구조 확인 결과

프론트엔드 규칙은 `.agents/rules/front-end/code-convention-react.md`, `.agents/rules/front-end/comment.md`, `.agents/rules/front-end/test.md`를 따른다.

## 구조 규칙

- 화면은 `page`, `container`, `component` 단위로 분리한다.
- `page`는 라우팅 진입점 역할만 담당한다.
- `container`는 API 호출, 상태 관리, 이벤트 흐름 등 화면의 로직을 담당한다.
- `component`는 UI 렌더링만 담당한다.
- 공통 UI는 `shared/ui`에 작성한다.
- 도메인별 화면과 컴포넌트는 `features/{domain}` 내부에 작성한다.
- 상태가 없는 화면에는 별도 hook을 만들지 않는다.

## 주석 규칙

- 모든 컴포넌트에는 Doc Comment를 작성한다.
- 모든 타입에는 Doc Comment를 작성한다.
- 타입의 모든 필드에는 측면 주석을 작성한다.
- 모든 함수와 Custom Hook에는 Doc Comment를 작성한다.
- 단순 JSX 렌더링이나 명확한 값 할당에는 불필요한 주석을 작성하지 않는다.

## 타입 규칙

- `any` 사용은 금지한다.
- API 요청 타입과 응답 타입은 분리한다.
- 화면에서 사용하는 데이터 형태가 API 응답과 다르면 ViewModel 타입을 별도로 작성한다.
- 현재는 API 연동 전 화면 구조 작업이므로 ViewModel과 임시 데이터를 우선 둔다.

## Next.js 구조

Next.js App Router 기준으로 새 라우트는 다음처럼 추가한다.

- `src/app/login/page.tsx`
- `src/app/signup/page.tsx`
- `src/app/me/page.tsx`

각 `page.tsx`는 해당 도메인의 Container만 호출한다.

현재 실제 코드 구조는 다음과 같다.

```text
src/app/
  page.tsx
  blog/page.tsx

src/features/
  platform/
  blog/

src/shared/ui/
  AppFrame.tsx
  AppTopBar.tsx
  BottomNavigation.tsx
  Icon.tsx
  NarrowContent.tsx
  WideContent.tsx
```

# 구현계획

## 1단계: README.md 최신화

현재 README.md는 실제 코드와 맞지 않으므로 먼저 갱신한다.

- `/community` 설명 제거
- `features/community` 설명 제거
- `/blog` 설명 추가
- `features/blog` 구조 반영
- 현재 플랫폼 홈 구조 반영
- `plan4` 기준 향후 화면 설계 방향 반영

README.md는 작업 히스토리를 남기는 문서가 아니라 프로젝트 구조, 아키텍처, 도메인 설명, 코드 규칙을 설명하는 문서로 유지한다.

## 2단계: 공통 UI 기반 정리

공통 UI는 `shared/ui`에 둔다.

### BrandLogo 추가

`src/shared/ui/BrandLogo.tsx`를 추가한다.

- `choimory.dev` 브랜드 표시
- `{}`, `/`, `.` 같은 개발 느낌의 특수문자 활용
- CSS 기반의 가벼운 애니메이션 적용
- 너무 장식적이기보다 상단바와 로그인 화면에서 재사용 가능한 형태로 구성

### AppTopBar 수정

`src/shared/ui/AppTopBar.tsx`를 수정한다.

- 기존 텍스트 브랜드를 `BrandLogo`로 교체
- 로그인 버튼을 단순 `button`에서 `/login`으로 이동하는 `Link`로 변경
- 추후 로그인 상태에 따라 로그인 버튼 대신 `/me` 진입을 보여줄 수 있게 props 구조를 준비
- 플랫폼 화면과 서비스 내부 화면에서 모두 재사용 가능하게 유지

### BottomNavigation 정책 정리

`src/shared/ui/BottomNavigation.tsx`는 공통 컴포넌트로 유지하되, 항목 구성은 각 화면에서 명확히 나눈다.

플랫폼용 하단 툴바 후보:

- 홈
- 서비스
- 알림
- 내 공간

blog용 하단 툴바 후보:

- 피드
- 인기
- 작성
- 홈

blog에서 `홈(플랫폼)`, `홈(블로그)`, `홈(내 블로그 홈)`, `검색`, `피드`, `글쓰기`를 모두 하단에 넣으면 항목이 많아지므로, 초기 구현에서는 4개 정도로 제한한다.

검색은 하단 탭보다는 상단 아이콘 또는 별도 검색 화면으로 분리하는 것이 좋다.

## 3단계: 인증 화면 추가

인증 도메인은 `features/auth`로 둔다.

추가할 파일 후보:

```text
src/app/login/page.tsx
src/app/signup/page.tsx

src/features/auth/model/authTypes.ts
src/features/auth/container/LoginContainer.tsx
src/features/auth/container/SignupContainer.tsx
src/features/auth/components/LoginView.tsx
src/features/auth/components/SignupView.tsx
```

### 로그인 화면

- 레거시 로그인 화면 느낌을 참고하되 현재 공통 프레임에 맞춘다.
- 회원가입 버튼을 로그인 화면 안에 제공한다.
- 실제 API 연동은 하지 않는다.
- submit 기본 동작만 막고 화면 구조를 먼저 만든다.

### 회원가입 화면

- 기본 회원가입 폼을 만든다.
- 이름 또는 닉네임, 이메일, 비밀번호, 비밀번호 확인 정도의 화면 필드를 둔다.
- 실제 API 연동, 이메일 인증, 가입 완료 화면은 다음 단계로 미룬다.

## 4단계: 마이페이지 화면 추가

마이페이지 도메인은 `features/me`로 둔다.

추가할 파일 후보:

```text
src/app/me/page.tsx

src/features/me/model/meTypes.ts
src/features/me/container/MeContainer.tsx
src/features/me/components/MeView.tsx
```

마이페이지 초기 화면 구성:

- 프로필 요약
- 개인정보 변경
- 사이트 설정
- 테마 설정
  - 라이트
  - 다크
  - 시스템
- 2차 인증 설정
  - 이메일 OTP
  - 모바일 OTP
- 회원 탈퇴

초기에는 실제 저장 기능 없이 화면 구조만 만든다.

## 5단계: 플랫폼 홈 분기 구조

현재 플랫폼 홈은 비회원 소개 섹션이 고정으로 들어가 있다.

`PlatformHomeViewModel`에 로그인 상태를 표현할 수 있는 필드를 추가한다.

예시:

```ts
authStatus: 'guest' | 'member';
```

비로그인 사용자:

- 검색바
- 서비스 런처
- 서비스 소개 랜딩 섹션
- 로그인/회원가입 CTA

로그인 사용자:

- 검색바
- 서비스 런처
- 사용자의 서비스별 피드 요약
- 최근 활동 또는 알림 요약

실제 인증이 없으므로 초기에는 임시 ViewModel 값으로 분기 구조만 만든다.

## 6단계: blog 화면 분기 구조

`BlogViewModel`에도 로그인 상태를 표현할 수 있는 필드를 추가한다.

비로그인 사용자:

- blog 소개
- 지금 뜨거운 게시글 또는 인기 게시글 피드
- 로그인/회원가입 CTA

로그인 사용자:

- 현재 구현된 개인 피드 중심 화면 유지
- 피드 필터
- 글 작성 진입 영역
- 게시글 카드

blog 하단 툴바는 우선 다음 4개로 둔다.

- 피드
- 인기
- 작성
- 홈

`내 블로그 홈`은 추후 프로필/마이페이지 또는 blog 내부 개인 페이지가 생긴 뒤 별도 라우트로 다루는 편이 좋다.

## 7단계: 서비스 종류 정리

서비스 런처의 실제 서비스와 더미 서비스를 구분한다.

1차 확정 후보:

- 블로그
- 메모
- 피드
- 가계부
- 일정

현재 서비스 런처에는 동작 확인용 더미 서비스가 포함되어 있으므로, 이후에는 `isPlaceholder` 같은 필드를 두거나 실제 서비스 후보와 화면 확인용 더미를 분리하는 것이 좋다.

## 8단계: 검증

구현 완료 후 다음 검증을 수행한다.

- `npx tsc --noEmit`
- `npm run lint`
- `npm run build`

단, 프로젝트 규칙상 테스트 수행도 사용자 허락을 받은 뒤 진행한다.

# 추가사항1

- 로고 애니메이션을 타이핑하는거처럼 글자 하나씩 치는걸로
- {choimory.dev/}를 {choimory.dev()}로 바꾸자
- 로그인 화면에서 회원가입 링크 연결 안되어있음
- 레거시 로그인화면 보면 네이버, 카카오, 구글 아이디로 로그인도 있는데 그거 빠졌음

## 추가사항1 구현계획

### BrandLogo 수정

- 표시 텍스트를 `{choimory.dev/}`에서 `{choimory.dev()}`로 변경한다.
- 글자 단위로 하나씩 나타나는 타이핑 애니메이션을 적용한다.
- 상단바처럼 작은 위치에서도 과하지 않도록 로고 컴포넌트 내부에 공통 애니메이션을 적용한다.
- `{`, `}`, `.`, `()`의 색상 분리는 유지한다.

### 전역 CSS 추가

- `globals.css`에 로고 타이핑용 `@keyframes`를 추가한다.
- 글자별 `span`에 지연 시간을 다르게 주는 방식으로 구현한다.
- width 기반 타이핑보다 글자별 애니메이션이 반응형 폭 계산 문제가 적고, 색상 분리도 유지하기 쉽다.

### 로그인 화면 회원가입 링크 개선

- 현재 `/signup` 링크 자체는 존재하지만, 화면에서 더 명확하게 보이도록 버튼 스타일로 개선한다.
- 로그인 버튼 아래에 보조 액션으로 회원가입 진입을 표시한다.

### 소셜 로그인 버튼 추가

- 로그인 화면에 소셜 로그인 영역을 추가한다.
- 네이버, 카카오, 구글 로그인 버튼을 표시한다.
- 실제 OAuth 연동은 아직 하지 않고, `type="button"`의 화면 요소로만 구성한다.
- 각 서비스의 인지 가능한 색상을 사용하되, 현재 다크 UI와 어울리도록 과한 장식은 피한다.

### 인증 ViewModel 확장

- `authTypes.ts`의 `LoginViewModel`에 `socialProviders`를 추가한다.
- 소셜 로그인 버튼 정보는 ViewModel에서 제공하고, `LoginView`는 렌더링만 담당한다.

예시:

```ts
type SocialLoginProvider = {
  id: 'naver' | 'kakao' | 'google';
  label: string;
};
```

### 검증

- 구현 후 다음 검증을 수행한다.
  - `npx tsc --noEmit`
  - `npm run lint`
  - `npm run build`

# 추가사항2

- 현재 로고 애니메이션은 글자마다 위아래로 움직여서 파도치는 wave 느낌이 난다.
- 원하는 방향은 커서가 깜빡이고 글자가 하나씩 나타나는 타자기 느낌이다.

## 추가사항2 구현계획

### BrandLogo 수정

- 글자별 `span` 애니메이션을 제거한다.
- `{choimory.dev()}` 전체를 하나의 텍스트로 렌더링한다.
- 색상 분리보다 타자기 느낌을 우선한다.

### 전역 CSS 수정

- 기존 `brand-logo-type`의 translate 기반 애니메이션을 제거한다.
- 로고 텍스트의 `max-width` 또는 `width`가 `0`에서 전체 글자 길이까지 열리도록 `steps()` 애니메이션을 적용한다.
- 커서는 오른쪽 border로 표현한다.
- 커서는 `blink` 애니메이션으로 깜빡이게 한다.
- `prefers-reduced-motion: reduce`에서는 애니메이션과 커서 깜빡임을 제거한다.

### 검증

- 구현 후 다음 검증을 수행한다.
  - `npx tsc --noEmit`
  - `npm run lint`
  - `npm run build`

# 추가사항3

- 로고의 타자기 애니메이션은 유지하되, 사라진 색상 분리를 다시 살리고 싶다.

## 추가사항3 구현계획

### BrandLogo 수정

- 로고 전체를 잘라내는 바깥 wrapper를 둔다.
- 바깥 wrapper에 `max-width: 0 -> 전체 글자 길이` `steps()` 애니메이션과 커서 border를 적용한다.
- wrapper 안쪽에는 글자별 `span`을 다시 사용해 색상 분리를 적용한다.
- 글자별 `span`에는 개별 이동 애니메이션을 주지 않는다.
- 이렇게 하면 wave 느낌 없이 왼쪽에서 오른쪽으로 잘리며 나타나는 타자기 효과를 유지하면서 색상 분리도 가능하다.

### 색상 기준

- `{`, `}`는 primary 색상으로 표시한다.
- `.`은 green 색상으로 표시한다.
- `(`, `)`는 orange 색상으로 표시한다.
- `choimory`, `dev`는 foreground 색상으로 표시한다.

### 전역 CSS 유지

- `brand-logo-typewriter`와 `brand-logo-caret` 애니메이션은 유지한다.
- 내부 색상 span에는 애니메이션을 적용하지 않는다.
- `prefers-reduced-motion: reduce` 대응은 유지한다.

### 검증

- 구현 후 다음 검증을 수행한다.
  - `npx tsc --noEmit`
  - `npm run lint`
  - `npm run build`
- 테스트 수행은 사용자 허락을 받은 뒤 진행한다.

# 추가사항4

- 플랫폼홈 모바일S (320px)에서 상단 로그인버튼 깨짐
- 블로그홈 모바일S (320px)에서 상단 로고 타이핑되면서 우측 요소들이 밀려나면서 화면 깨짐
- 플랫폼홈 태블릿 (768px)에서 좌우 마진이 없이 딱붙어있음 (다른 레이아웃은 마진 조금 남아있음)

## 추가사항4 분석

### 플랫폼 홈 모바일S 상단 로그인 버튼 깨짐

원인 후보:

- `AppTopBar` 내부가 `h-16 flex items-center gap-3 px-4` 구조다.
- 왼쪽 로고, 검색 버튼, 알림 버튼, 로그인 버튼이 한 줄에 모두 배치되어 있다.
- 320px 폭에서는 로고 타이핑 폭, 아이콘 2개, 로그인 버튼, gap이 합쳐져 공간이 부족하다.
- 로그인 버튼 텍스트가 압축되거나 요소들이 서로 밀리면서 깨질 가능성이 높다.

확인 대상:

- `src/shared/ui/AppTopBar.tsx`
- `src/shared/ui/BrandLogo.tsx`

해결 후보:

- 모바일S에서는 검색/알림 아이콘을 숨긴다.
- 로그인 버튼의 좌우 padding을 줄이고 `shrink-0`을 준다.
- 로고 영역을 `min-w-0`, `max-w`로 제한한다.
- 상단바 액션을 화면 폭별로 다르게 보여준다.

### blog 홈 모바일S 로고 타이핑 중 화면 깨짐

원인 후보:

- `BrandLogo`가 `max-width: 0 -> 전체 폭`으로 커지며 실제 레이아웃 폭을 점점 차지한다.
- `AppTopBar`에서 로고가 flex 아이템으로 들어가 있어, 타이핑 중 로고 폭 변화가 우측 아이콘과 버튼을 밀어낸다.
- blog 화면은 `leading` 뒤로가기 버튼까지 있어 플랫폼 홈보다 가로 공간이 더 부족하다.

핵심 원인:

- 애니메이션이 `width` 또는 `max-width`를 변경하고 있고, 이 변경이 상단바 레이아웃에 영향을 준다.

해결 후보:

- 로고 wrapper의 최종 폭을 처음부터 고정하고 내부 텍스트만 clip 되게 한다.
- 또는 `BrandLogo`에 애니메이션 옵션을 추가하고 상단바에서는 애니메이션을 끈다.

추천 방향:

- 상단바에서는 로고 애니메이션을 끈다.
- 플랫폼 홈 메인 타이틀에서는 로고 애니메이션을 유지한다.
- 이렇게 하면 상단바 레이아웃이 안정되고, 홈 메인에서는 타자기 효과를 계속 보여줄 수 있다.

### 플랫폼 홈 태블릿 768px 좌우 마진 없음

원인 후보:

- `WideContent`는 `max-w-[768px] px-4 md:px-0` 구조다.
- Tailwind의 `md`는 768px부터 적용된다.
- 따라서 정확히 768px viewport에서는 `md:px-0`이 적용되어 좌우 padding이 0이 된다.
- `AppTopBar`도 `px-4 md:px-0` 구조라 768px에서 좌우 여백이 사라질 수 있다.

핵심 원인:

- `md:px-0`이 768px부터 적용되고, `max-w-[768px]`와 viewport 768px가 만날 때 좌우 여백이 사라진다.

해결 후보:

- `md:px-0`을 제거하고 항상 `px-4`를 유지한다.
- 또는 `md:px-4 lg:px-0`로 변경하여 768px에서는 여백을 유지하고 큰 화면에서만 padding을 제거한다.
- 또는 `max-w-[768px]` 자체를 줄인다.

추천 방향:

- `WideContent`, `AppTopBar`는 768px에서도 좌우 여백을 유지하도록 `md:px-0`을 제거하거나 `lg:px-0`로 늦춘다.
- 768px 태블릿에서도 여백이 남아야 다른 레이아웃과 시각적으로 맞다.

## 추가사항4 구현계획

### BrandLogo 옵션 추가

- `BrandLogo`에 `isAnimated?: boolean` 옵션을 추가한다.
- 기본값은 `true`로 둔다.
- `AppTopBar`에서는 `isAnimated={false}`로 사용한다.
- 플랫폼 홈 메인 타이틀에서는 기존처럼 애니메이션을 유지한다.

### BrandLogo 애니메이션 구조 보정

- 상단바에서는 애니메이션을 끄므로, 로고 폭 변화로 우측 요소가 밀리는 문제를 제거한다.
- 필요한 경우 애니메이션 로고의 바깥 폭을 고정하고 내부만 clip하는 구조도 검토한다.

### AppTopBar 모바일S 대응

- 상단바의 로고 영역은 `min-w-0`과 적절한 `max-w`를 둔다.
- 모바일S에서는 검색/알림 아이콘을 숨긴다.
- 로그인 버튼은 `shrink-0`, 작은 padding으로 깨지지 않게 한다.
- blog 화면처럼 뒤로가기 버튼이 있는 경우에도 `뒤로가기 + 로고 + 로그인` 정도만 안정적으로 남긴다.

### 768px 마진 보정

- `AppTopBar`의 `md:px-0`을 제거하거나 `lg:px-0`로 변경한다.
- `WideContent`의 `md:px-0`을 제거하거나 `lg:px-0`로 변경한다.
- 필요하면 `BottomNavigation`도 wide 기준에서 좌우 여백을 확인한다.

### 검증

- 구현 후 다음 검증을 수행한다.
  - `npx tsc --noEmit`
  - `npm run lint`
  - `npm run build`
- 가능하면 320px, 768px viewport에서 화면을 확인한다.

# 추가사항5

- 블로그홈 320px에서 상단 로고의 `/ blog`가 사라진다.
- 320px에서 줄바꿈이 되더라도 `/ blog`까지 표시됐으면 좋겠다.
- `choimory.dev`는 플랫폼 홈으로 이동하는 링크로 사용한다.
- `/ blog`는 블로그 홈으로 이동하는 링크로 사용할 수 있다.

## 추가사항5 구현계획

### AppTopBar 브랜드 영역 구조 변경

- `AppTopBar`의 브랜드 영역을 별도 wrapper로 묶는다.
- 현재는 `leading`, `BrandLogo`, `/ blog`, 우측 액션이 한 줄에 가까운 구조다.
- 브랜드 영역은 좁은 화면에서 세로로 쌓일 수 있게 만든다.
- 320px에서는 첫 줄에 `choimory.dev`, 둘째 줄에 `/ blog`가 표시되어도 된다.

### 서비스명 숨김 제거

- 현재 작은 화면에서 `/ blog`를 숨기기 위해 넣은 `hidden min-[360px]:inline` 계열 처리를 제거한다.
- 대신 작은 화면에서는 줄바꿈 또는 세로 배치로 `/ blog`를 유지한다.

### 서비스명 링크화

- `AppTopBar`에 `serviceHref?: string` 옵션을 추가한다.
- `serviceName`과 `serviceHref`가 모두 있으면 `/ blog`를 링크로 렌더링한다.
- `serviceHref`가 없으면 기존처럼 텍스트로 렌더링한다.
- blog 화면에서는 `serviceName="blog"`와 `serviceHref="/blog"`를 전달한다.

### 상단바 높이 조정

- 현재 상단바는 `h-16` 고정이라 두 줄 표시 시 답답하거나 깨질 수 있다.
- `min-h-16 py-2`처럼 자연스럽게 늘어날 수 있는 구조로 변경한다.
- 큰 화면에서는 기존처럼 한 줄 느낌을 유지한다.

### 우측 액션 보호

- 320px에서는 검색/알림 숨김 정책을 유지한다.
- 로그인 버튼은 `shrink-0`으로 유지한다.
- 뒤로가기 버튼이 있는 blog 화면에서도 `뒤로가기 + 브랜드 영역 + 로그인 버튼` 조합이 깨지지 않게 한다.

### 검증

- 구현 후 다음 검증을 수행한다.
  - `npx tsc --noEmit`
  - `npm run lint`
  - `npm run build`
- 가능하면 320px blog 화면에서 `/ blog`가 보이는지 확인한다.
