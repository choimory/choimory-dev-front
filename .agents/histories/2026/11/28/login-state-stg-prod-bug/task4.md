# 개요

- task3에서 구현한 프록시 서버 검증 이후, 사용자가 발견한 버그를 분석하고 고친 기록이다.
- 비로그인 상태에서 하단 `내 정보`를 눌러 로그인 화면으로 이동한 뒤 로그인하면, 로그인 API는 성공하는데 화면이 로그인 화면에 머문다.
- task3의 브라우저 확인은 보호 페이지 URL을 직접 열어서(전체 페이지 로드) 들어가는 경우만 다뤘고, 이 버그는 링크를 눌러 클라이언트 이동으로 들어가는 경우에만 나타난다. 그래서 task3 검증에서 걸러지지 않았다.
- 이 문서는 작업이 끝난 뒤에 작성했다.

# 로그인 후 이동 실패 수정

> 비로그인상태에서 내정보 눌러서 로그인창으로 이동했을때 로그인이 안됨 확인해봐

## 답변

원인은 클라이언트 라우터가 `/me`의 리다이렉트 결과를 캐시하고 로그인 후 `router.push('/me')`가 그 캐시를 재사용하는 것이다. 로그인 후 이동을 전체 페이지 이동(`hardNavigate`)으로 바꿔서 고쳤고, 사용자가 말한 순서 그대로 브라우저에서 다시 확인했다.

## 현상과 재현

paseo 브라우저로 local(`localhost:3000`)에서 같은 순서로 재현했다.

1. 로그아웃(쿠키 없음) 상태로 홈(`/`)을 연다.
2. 하단 `내 정보`를 클릭한다. → `/login?next=%2Fme`로 이동한다. (여기까지는 정상)
3. 이메일과 비밀번호를 입력하고 `로그인`을 누른다.
4. 결과: `/api/auth/login`은 200으로 성공하지만, 화면은 `/login?next=%2Fme`에 그대로 머문다. 오류 메시지도 없다.

네트워크 기록에서 확인한 것

- 클릭 시점에 `/me?_rsc=...` 요청(200)이 한 번 나갔다.
- 로그인 직후에는 `/me`로 가는 요청이 없었다. (`router.push`가 서버에 요청하지 않았다.)

## 원인 분석

가설: 비로그인으로 처음 `/me`에 클라이언트 이동했을 때 프록시가 `/login?next=%2Fme`로 리다이렉트하고, 클라이언트 라우터가 이 결과를 `/me`의 캐시로 저장한다. 로그인 후 `router.push('/me')`는 서버에 다시 요청하지 않고 그 캐시를 쓰기 때문에 다시 로그인 화면으로 간다.

가설을 확인한 과정 (로그인으로 쿠키가 이미 설정된 상태, 막힌 화면에서 실행)

| 시도 | 결과 |
|---|---|
| `window.next.router.push('/me')` | `/login?next=%2Fme`에 머묾 |
| `router.refresh()` 후 `push('/me')` | 여전히 머묾. `refresh()`는 현재 경로(`/login`)만 갱신해서 `/me`의 캐시를 지우지 못한다. |
| `window.next.router.push('/me?x=1')` (캐시에 없는 URL) | `/me?x=1`로 이동, 마이페이지가 보이고 상단바 `로그아웃` |

- 마지막 결과로 로그인 상태와 쿠키, 프록시는 정상이고 `/me` 경로의 클라이언트 캐시만 문제임이 확인됐다.
- 전체 페이지 로드로 `/me`를 여는 것은 task3에서 확인했듯 정상이다. 그래서 직접 URL로 들어가는 경우에는 이 버그가 보이지 않는다.

조사 중 헛다리: 같은 쿠키로 `curl`에 `RSC: 1` 헤더를 붙여 `/me`를 호출하니 리다이렉트가 와서 프록시 문제처럼 보였다. 하지만 이는 `_rsc` 캐시 해시를 제가 잘못 만들어서 Next가 올바른 해시를 붙이도록 보낸 자체 리다이렉트(`/me?_rsc=<해시>`)였고, 프록시와 무관했다. 이 결과로는 프록시를 의심하지 않았다.

## 수정 내용

로그인 성공 후 이동을 `router.push(redirectTo)`에서 `hardNavigate(redirectTo)`(`window.location.assign`)로 바꿨다. 새 쿠키를 가지고 서버에 다시 요청하므로 클라이언트 캐시를 거치지 않는다. 로그아웃 후 이동에 이미 쓰고 있는 방식과 같다.

- `src/features/auth/container/LoginContainer.tsx`: `useRouter` 제거, `hardNavigate(redirectTo)` 호출. 이유를 JSDoc에 남겼다. (클라이언트 라우터가 비로그인 방문 때의 리다이렉트 결과를 캐시해 재사용하므로 클라이언트 이동으로는 로그인 후 같은 경로로 이동하지 못한다.)
- `tests/unit/features/auth/container/LoginContainer.test.tsx`: `next/navigation` mock 대신 `@/shared/navigation/hardNavigate`를 mock한다. 로그인 성공 시 `/`(기본), `redirectTo`(`/feed/me`)로 `hardNavigate`가 호출되는지, 실패하면 호출되지 않는지 확인한다.

대가: 로그인 후 페이지가 한 번 새로고침된다. 로그인 직전 메모리에 있던 Access Token은 새 페이지에서 `AuthProvider`가 `restoreSession`으로 다시 복원한다.

## 검증 결과

- 브라우저(paseo, `localhost:3000`, 테스트 계정): 재현했던 순서와 똑같이 확인했다.
  - 로그아웃 → 홈 → `내 정보` 클릭 → `/login?next=%2Fme` → 로그인
  - 결과: `/me`로 이동, 마이페이지 표시, 상단바 `로그아웃`
- `npx tsc --noEmit`: 에러 없음
- `npx eslint src tests vitest.setup.ts`: 에러 0건, 경고 0건
- `npx vitest run`: 102개 파일, 668건 통과
- 인증 영역만 따로 돌린 결과: 10개 파일, 75건 통과

## 확인하지 못한 것

- stg와 prod: 일반적으로 Next.js의 링크 프리페치는 production 빌드에서 동작하고 `next dev`에서는 동작하지 않는다. (이 부분은 문서로 확인하지 못했고 일반 지식에 근거한다.) 프록시는 프리페치 요청을 건너뛰므로, production에서는 `내 정보` 링크가 프리페치되어 비로그인으로 클릭했을 때의 흐름이 local과 다를 수 있다. 배포 후 `내 정보` 클릭 → 로그인 → 원래 페이지 복귀를 stg에서 다시 확인해야 한다.
- 다른 보호 경로(`/blog/me`, `/feed/me` 등)의 같은 시나리오를 각각 브라우저로 확인하지는 않았다. 수정이 모든 로그인 성공 후 이동에 공통으로 적용되어 같은 원인이면 함께 해결된다고 판단했다.
- 로그인과 회원가입 사이에서 `next`를 유지하지 않는 것은 이전 결정(후속)대로이며 이번 수정과 무관하다.

## 남은 것

- stg 배포 후 위 흐름 확인 (배포는 메인이 진행하지 않는다)
- 후속 후보: 로그인 후 새로고침 없이 이동하는 방법(클라이언트 이동과 캐시 무효화)을 다시 검토할 수 있다. `router.refresh()`만으로는 해결되지 않았다.
- 프론트와 `member-api` 변경은 모두 커밋되지 않았다. 커밋은 사용자가 지시한다.
- 테스트 계정 `tokentest01@example.com`이 local과 stg DB에 남아 있다. (비밀번호는 문서에 적지 않음)
- `README.md`와 `done` 문서, calendar `DONE` 전환은 마무리를 요청받았을 때 한다.
