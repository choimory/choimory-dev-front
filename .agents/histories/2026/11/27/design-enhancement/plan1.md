# hallmark redesign 전체 페이지 적용 검토

> hallmark redesign 사용하려하는데 앱의 모든 페이지를 대상으로 할까 싶음 (로고만 빼고)

## 답변

hallmark redesign으로 전체 페이지를 가는 건 괜찮다고 봄. 다만 21개 페이지를 한 번에 하기보다는 단계를 나누는 걸 추천함. 현재 구조와 hallmark redesign 규칙(`.agents/skills/hallmark/references/redesign.md`)을 보고 정리함.

## 현재 상태

- **페이지 21개**
  - 진입·인증: `/`, `/services`, `/notice`, `/login`, `/signup`, `/me`
  - 블로그 7개: `/blog`, `popular`, `following`, `me`, `[nickname]`, `users/[nickname]`, `posts/[postId]`
  - 피드 8개: `/feed`, `popular`, `observations`, `activities`, `targets`, `me` 등
- **공용 UI**: `src/shared/ui`에 18개(AppFrame, AppTopBar, BottomNavigation, Button, Card, Chip, ListRow, Modal 등)가 있음. 대부분의 화면이 이걸 같이 쓰고 있어서, 여기와 토큰만 바꿔도 전체 톤이 크게 달라짐.
- **로고**: `src/shared/ui/BrandLogo.tsx`와 `globals.css`의 `brand-logo-typewriter`·`brand-logo-caret` 애니메이션. 이 둘은 건드리지 않는 대상으로 둠.
- **스택**: Next 16, Tailwind v4, 별도 디자인 시스템 없음, 테스트는 `tests/unit`에 있음.

## 알아둘 hallmark redesign 규칙

- **내용·동작 유지**: 문구, 링크, 폼, 핸들러, `id`, `data-testid`는 유지함. 테스트를 고쳐서 통과시키는 것도 금지. 그래서 기존 테스트가 마크업 구조에 의존하면 그게 제약이 됨.
- **페이지가 여러 개일 때**: 먼저 디자인 시스템을 `design.md`로 고정하고, 모든 페이지가 그걸 공유함. 페이지마다 다른 건 화면 구성뿐.
- **앱 화면 기준**: 지금 셸(AppFrame, 탑바, 하단 내비) 안에서 화면마다 무엇을 앞세울지와 배치를 다시 짬. 라우트와 로직은 그대로.
- **깊이 3단계**
  - **full**: 시스템과 구성을 모두 바꿈.
  - **restyle**: 레이아웃은 두고 색·타입·라운드·모션만 바꿈.
  - **polish**: 티 나는 부분만 고침.
- **사전 준비**: git이 깨끗해야 함(현재 clean). dev 서버를 띄워서 before 스크린샷을 찍음. 끝나면 before/after 비교 파일(`.hallmark/compare.html`)이 생김.

## 추천 진행안

1. **사전 기록**: 전 페이지 before 스크린샷과 점검 결과(audit)를 남김.
2. **시스템 확정**: 테마를 고르고 토큰을 만든 뒤 `design.md`로 고정.
3. **공용 UI와 셸 redesign**: `shared/ui`(로고 제외)와 `globals.css`를 바꿈. 이 단계에서 전체 톤이 바뀜.
4. **페이지 redesign**: 많이 보는 순서로 진행. 홈 `/` → 블로그 → 피드 → 인증·마이·공지·서비스 순이고, 한 도메인이 끝날 때마다 확인받음.
5. **검증**: 유지 항목 확인, 타입 체크, 빌드, 테스트 실행.

전 페이지를 full로 하면 변경량이 아주 큼. 그래서 3단계까지 하고 결과를 본 다음, 페이지별로 full로 갈지 restyle로 끝낼지 정하는 것도 방법.

## 정해야 할 것

1. **깊이**: 전 페이지 full로 갈지, 공용 UI와 시스템 위주(restyle 성격)로 갈지.
2. **로고 범위**: 로고 컴포넌트만 유지할지, 로고에 쓰인 색·폰트까지 브랜드 기준으로 삼아 새 시스템에 반영할지.
3. **hallmark가 물어볼 것**: 지금 디자인에서 마음에 안 드는 점, 원하는 느낌(editorial, utilitarian, technical, soft 같은 극단적인 톤 하나), 기준 색. 아니면 "go ahead"로 맡김.
4. **진행 방식**: 4단계를 페이지별 서브에이전트로 나눠 병렬로 할지, 순서대로 할지.

# 결정사항 1차 (깊이, 로고, 톤, 진행방식)

> 1. full과 restyle 차이가 뭐임?
> 2. 로고는 그냥 노터치
> 3. 톤과 색은 go ahead
> 4. 페이지별로 병렬할껀데 일단은 작업계획부터 세우고 나눌생각

## 답변

- 톤과 색은 go ahead로 확정.
- 페이지별 병렬 진행을 생각한다면 full이 맞는 선택.
- 로고는 노터치하되, 토큰 의존 문제로 방식(A/B/C) 결정이 필요함.
- 다음은 병렬로 나누기 위한 작업계획 수립.

## full과 restyle 차이

| | restyle | full |
|---|---|---|
| **유지** | 레이아웃: 화면 구조, 섹션 순서, 카드·리스트 배치 | 내용과 동작만 (문구, 링크, 폼, 핸들러, 라우트) |
| **변경** | 디자인 시스템: 색, 폰트, 크기 체계, 라운드, 그림자, 모션, 버튼·칩 같은 컨트롤 모양 | 시스템 + 화면 구성: 무엇을 앞세울지, 배치, 셸(탑바·하단 내비) |
| **이 앱에서 예를 들면** | 피드 목록이 지금처럼 카드 리스트인 건 그대로, 카드의 생김새만 바뀜 | 피드 목록이 카드 리스트에서 타임라인형이나 밀도 높은 표 형태로 바뀔 수도 있음 |
| **작업량·리스크** | 주로 `globals.css`, 토큰, `shared/ui`만 수정. 테스트 영향 적음 | 21개 페이지 컴포넌트의 마크업 대부분 수정. 테스트 영향 큼 |
| **결과 체감** | "같은 앱인데 다듬어짐" | "다른 앱처럼 보임" |

restyle은 사실상 공용 UI와 토큰 작업이라 병렬로 나눌 게 별로 없음. 페이지별 병렬을 생각한다면 full이 맞는 선택.

## 로고 노터치 관련 확인 필요

`BrandLogo.tsx`는 자체 색이 없고 테마 토큰을 그대로 가져다 씀.

- `{ }`는 `--primary`, `.`는 `--accent-green`, `( )`는 `--accent-orange`, 본문은 `--foreground`
- 폰트는 Tailwind 기본 `font-mono`
- 다크/라이트 테마 값이 각각 따로 있음

그래서 파일을 안 건드려도, 새 시스템이 이 토큰 값을 바꾸면 로고 색이 같이 바뀜. 선택지는 세 가지.

- **A. 토큰 값 고정**: 위 토큰의 현재 값(다크/라이트 둘 다)을 새 팔레트에서도 그대로 유지. 로고 파일은 0줄 수정. 대신 새 시스템의 메인 색이 지금 파란색(`#7aa2ff`/`#2563eb`)에 묶임.
- **B. 로고 전용 토큰 분리 (추천)**: `--logo-brace`, `--logo-dot` 같은 로고 전용 토큰을 현재 값으로 만들고, BrandLogo의 클래스명만 그 토큰으로 바꿈. 겉모습은 100% 그대로이고, 새 시스템은 색을 자유롭게 고를 수 있음. 다만 로고 파일의 클래스명 몇 줄이 바뀜.
- **C. CSS로만 덮어쓰기**: `globals.css`에서 로고 요소에만 토큰을 옛 값으로 다시 지정. 파일은 안 건드리지만, 셀렉터가 `aria-label` 같은 것에 의존하게 돼서 꼼수에 가까움.

"노터치"가 겉모습을 지키는 의미라면 B를 추천하고, 파일 자체를 지키는 의미라면 A나 C.

## 다음 단계

2. **병렬 작업 단위 나누기**: 도메인 기준으로 나눔.
   - 홈·서비스·공지
   - 인증(로그인·회원가입)·마이

3. **통합 검증 (순차)**: 전체 sweep, 빌드·테스트, before/after 비교.

# 결정사항 2차 및 마크업 의존도 조사

> 1. full로 가자
> 2. 로고는 B
> 3. 조사 시작

## 답변

- 깊이는 **full**, 로고는 **B안(로고 전용 토큰 분리)**으로 확정.
- 조사 결론: 도메인끼리는 병렬로 깔끔하게 나눌 수 있음. 다만 테스트 쪽에 미리 정해야 할 제약이 하나 있음.

## 병렬로 나눌 수 있는지

- **도메인 간 의존**: `src/features`의 auth, blog, feed, me, platform 사이에 서로 import하는 곳이 하나도 없음. 도메인별로 나눠도 파일 충돌이 안 남.
- **공용 UI**: 모든 도메인이 `shared/ui`를 많이 씀(Icon 29곳, AppFrame·탑바·하단내비 각 15곳, Card 14곳, ListRow 13곳). 그래서 이 부분은 병렬 전에 한 번에 끝내야 함.
- **페이지 파일**: `src/app/**/page.tsx`는 거의 컨테이너만 부르는 얇은 파일. 실제 작업은 `features/*/components`에서 함. `blog/users/[nickname]`는 리다이렉트만 해서 대상에서 빠짐.
- **도메인별 규모**: 피드가 가장 큼(컴포넌트 20여 개, 차트·3D 캐러셀 포함). 다음이 블로그, 그다음 platform이고, auth·me가 가장 작음.

## 테스트 제약

- **역할·텍스트로 찾는 쿼리**: `getByRole` 596개, `getByText` 198개, `getByLabelText` 79개 등 대부분. 문구와 접근성 구조만 유지하면 full redesign에서도 깨지지 않음. `data-testid`는 사실상 없음.
- **클래스명 검증**: 37개 파일에 약 108개. full redesign에서 깨지는 건 주로 여기.
  - **상태를 클래스로 확인하는 것**: 선택된 탭이나 버튼을 `bg-primary`, `border-primary`로, 비활성을 `opacity-75`로 확인.
  - **색 의미 확인**: 상승·하락 같은 걸 `text-accent-red`, `text-primary`, `text-muted`로 확인.
  - **구조·크기 확인**: `h-12`, `size-10`, `rounded-full`, `justify-end` 등.
  - **애니메이션**: `blog-ranking-enter`, `animationDelay` 140ms 간격.
  - 가장 많은 곳은 `ListRow` 11개, `BlogPostCreateModal`·`BlogPopularInsightSection` 각 7개.
- **hallmark 규칙과 충돌**: hallmark 규칙상 redesign을 통과시키려고 테스트를 고치는 건 금지. 그대로 full로 가면 이 108개가 큰 족쇄가 됨.

## 대응안

- **토큰 이름은 유지하고 값만 교체 (꼭 하기)**: `primary`, `surface`, `accent-*`, `muted` 같은 이름은 그대로 두고, 새 시스템의 색을 그 이름에 넣음. 그러면 색·상태를 확인하는 테스트 대부분이 그대로 통과함.
- **나머지 처리 방식 (선택)**: 그래도 깨지는 구조·크기 테스트(`h-12`, `size-10` 등)를 어떻게 할지 결정 필요.
  - **가. 테스트 수정 허용 (추천)**: 스타일만 확인하는 테스트는 승인된 목록 안에서만 수정을 허용. 상태 확인은 가능하면 `aria-pressed`, `aria-selected` 같은 의미 있는 속성으로 바꿈. 어떤 테스트를 고쳤는지는 전부 기록.
  - **나. 테스트 수정 금지**: 테스트는 건드리지 않고, 걸린 클래스는 새 디자인에서도 유지. 그만큼 디자인 자유도가 줄어듦.

## 그 외 확인한 것

- **로고 B안 보강**: 로고는 색 외에 폰트 `font-mono`(Geist Mono)도 씀. 로고 전용 토큰을 만들 때 폰트도 함께 고정해야 함. `BrandLogo.test.tsx`는 `text-xl`, `brand-logo-typewriter`만 확인해서 B안으로 가도 안 깨짐.
- **하드코딩 색**: 로그인 화면의 네이버(`#03c75a`)·카카오(`#fee500`) 버튼 색뿐. 다른 회사의 브랜드 색이라 그대로 둠.
- **라이트 테마**: `[data-theme="light"]` 토큰은 정의돼 있지만, 코드에서 이걸 켜는 곳은 찾지 못함. 새 시스템에서 라이트 테마를 유지할지 결정 필요. 지금은 다크 고정으로 보임.

## 작업계획에 반영할 병렬 구조 (초안)

| 단계 | 방식 | 범위 |
|---|---|---|
| 0. 사전 기록 | 순차 | 전 페이지 before 스크린샷과 audit |
| 1. 시스템 | 순차 | 테마 결정, 토큰(기존 이름 유지), 로고 전용 토큰, `design.md` 고정 |
| 2. 공용 UI·셸 | 순차 | `shared/ui` 17개(로고 제외), `globals.css` |
| 3-A | 병렬 | platform: `/`, `/services`, `/notice` |
| 3-B | 병렬 | auth와 me: `/login`, `/signup`, `/me` |
| 3-C | 병렬 | blog: 6개 화면 |
| 3-D | 병렬 | feed: 8개 화면 |
| 4. 통합 검증 | 순차 | sweep, 빌드·테스트, before/after 비교 |

3단계 작업자는 자기 `features/{도메인}`만 수정하고, `shared/ui`와 토큰은 건드리지 않음. 바꿔야 할 게 생기면 따로 보고하게 함.

## 남은 결정

1. 깨지는 테스트를 가(승인된 목록 안에서 수정 허용)와 나(수정 금지) 중 어떻게 할지.
2. 라이트 테마를 유지할지, 다크만 갈지.

# 결정사항 3차 및 작업계획 수립

> 1. 가
> 2. 유지

## 답변

- 테스트는 **가(승인한 목록 안에서만 수정)**, 라이트 테마는 **유지**로 확정.
- 이를 반영해 전체 작업계획을 정리함.

## 확정 사항

| 항목 | 결정 |
|---|---|
| 깊이 | full (내용과 동작만 유지하고, 디자인 시스템과 화면 구성 변경) |
| 범위 | 전 페이지 20개 (리다이렉트 1개 제외), 로고 제외 |
| 로고 | B안: 로고 전용 토큰(색 + 폰트)을 현재 값으로 고정하고, `BrandLogo.tsx`는 클래스명만 교체 |
| 톤·색 | go ahead (hallmark가 정한 뒤 알려줌) |
| 토큰 | 기존 이름(`primary`, `surface`, `accent-*`, `muted` 등)을 유지하고 값만 교체 |
| 테스트 | 승인한 목록 안에서만 수정. 상태 확인은 `aria-*` 속성 쪽으로 전환하고, 수정 내역은 전부 기록 |
| 테마 | 다크·라이트 둘 다 새 시스템으로 설계. 기본은 지금처럼 다크이고, 테마 전환 기능은 지금 없어서 새로 만들지 않음 |
| 진행 | 공통 작업은 순차, 도메인 4개는 병렬 |

## 작업계획

### 0단계. 사전 기록

순차, 직접 진행.

- dev 서버를 띄우고 전 페이지 before 스크린샷과 audit를 기록.
- 테스트를 한 번 돌려서 기준선(현재 통과 수)을 남김.
- 결과는 화면별 진단 형태로 공유: 무엇이 잘 되고 있는지, 어디가 AI가 만든 티가 나는지.

### 1단계. 디자인 시스템

순차.

- hallmark가 테마와 방향을 정하면, 시작 전에 보고.
- 기존 토큰 이름에 새 값을 넣음(다크·라이트 둘 다). 로고 전용 토큰도 만듦.
- `design.md`로 시스템을 고정. 이후 병렬 작업자들은 전부 이걸 기준으로 작업.

### 2단계. 공용 UI와 셸

순차.

- `shared/ui` 17개(로고 제외)와 `globals.css`를 바꿈.
- 깨지는 테스트가 생기면 목록을 만들어 승인받은 뒤 수정.
- 이 단계가 끝나면 결과를 확인받고 3단계로 넘어감.

### 3단계. 도메인별 화면

병렬, 서브에이전트 4개.

| 단위 | 화면 | 주요 파일 |
|---|---|---|
| A. platform | `/`, `/services`, `/notice` | `features/platform` |
| B. auth·me | `/login`, `/signup`, `/me` | `features/auth`, `features/me` |
| C. blog | 블로그 6개 화면 | `features/blog` |
| D. feed | 피드 8개 화면 | `features/feed` |

병렬 작업자 규칙.

- 자기 `features/{도메인}`과 해당 테스트만 수정. `shared/ui`, 토큰, `design.md`, `globals.css`는 건드리지 않음.
- 공용 쪽 변경이 필요하면 직접 고치지 않고 보고만 함. 통합 단계에서 반영.
- 깨지는 테스트는 바로 고치지 않고 수정안 목록으로 올림. 모아서 승인받은 뒤 반영.
- 도메인마다 완료 조건: 유지 항목(링크·폼·핸들러·문구) 확인, 해당 도메인 테스트 통과, 타입 체크 통과.
- 같은 작업 트리를 쓰되 파일이 겹치지 않게 나눔. hallmark의 `.hallmark/` 산출물만 도메인별 경로로 분리.

### 4단계. 통합 검증

순차.

- 전체 sweep(유지 항목 대조)을 하고, 타입 체크·린트·빌드·테스트를 전부 실행.
- before/after 비교 파일을 만들고, 바뀐 문구·수정한 테스트 목록을 정리.

## 확인할 점

- **확인 지점**: 1단계 시스템 확정 후, 2단계 공용 UI 완료 후, 3단계 시작 전 세 번 멈추고 확인받음.
- **커밋**: 단계별로 끊을지는 그때 확인. 임의로 커밋하지 않음.

# 진행 방식 확정 (단계별 끊기, 순차는 단독, 병렬은 GPT)

> 아까 이야기했던 섹션별로 작업완료되면 그때그때 끊어가면서 진행할거고 그 중 순차작업은 너 혼자 작업할거야
>
> 병렬작업할때 되면 gpt sol 6.2한테 도메인이나 페이지별로 시켜서 병렬작업하자

## 답변

- 단계가 끝날 때마다 끊어서 확인받으며 진행.
- 순차 단계(0·1·2·4)는 Claude 단독 작업.
- 병렬 단계(3)는 GPT Sol 6.2 여러 개에게 도메인별 또는 페이지별로 나눠 맡김.

## 진행 방식

| 단계 | 담당 | 끊는 지점 |
|---|---|---|
| 0. 사전 기록 | Claude 단독 | 완료 후 결과 공유하고 멈춤 |
| 1. 디자인 시스템 | Claude 단독 | 테마·토큰·`design.md` 확정 후 멈춤 |
| 2. 공용 UI·셸 | Claude 단독 | 완료·테스트 승인 후 멈춤 |
| 3. 도메인별 화면 | GPT Sol 6.2 여러 개 (도메인별 또는 페이지별) | 전원 완료 후 멈춤 |
| 4. 통합 검증 | Claude 단독 | 완료 후 결과 공유 |

## 3단계가 GPT에게 넘어가면서 달라지는 점

- **작업 지시서**: 서브에이전트가 아니라 다른 모델이라, 이 대화 맥락을 모르는 상태로 시작함. 그래서 2단계가 끝날 때 도메인별(또는 페이지별) 작업 지시서를 만들어 둠. 지시서에 담을 내용.
  - 기준 문서: `design.md`, hallmark `redesign.md`
  - 담당 파일 목록, 수정 금지 영역(`shared/ui`·토큰·`globals.css`·로고)
  - 유지 규칙: 문구·링크·폼·핸들러·접근성 구조
  - 깨지는 테스트는 직접 고치지 말고 수정안 목록으로 제출
  - 완료 조건과 보고 양식
- **hallmark 실행 방식**: GPT 쪽(Codex 계열)은 `$hallmark`로 호출. hallmark 쪽에도 Codex는 `flow.md` § Harnesses를 먼저 읽으라고 되어 있어서, 이 내용도 지시서에 넣음.
- **나누는 단위**: 도메인 4개(A~D)가 기본. 피드가 가장 크니 피드만 페이지별로 더 쪼개는 것도 가능. 그때 상황 보고 결정.
- **결과 취합**: GPT 작업자들이 보고하면 공용 쪽 변경 요청과 테스트 수정안을 모아서 승인받고, 4단계로 넘어감.

## 확인할 점

- GPT 작업자 실행을 사용자가 직접 할지, Claude가 paseo로 띄울지 결정 필요. 3단계 직전에 정해도 됨.
