# 2단계 공용 UI와 셸 계획

> 다음단계는 뭐지?

## 답변

2단계는 **공용 UI와 셸 redesign**. 모든 화면이 함께 쓰는 `src/shared/ui` 컴포넌트 17개(로고 제외)를 Cobalt 시스템에 맞게 다시 만드는 단계.

## 컴포넌트별 변경 내용

| 컴포넌트 | 지금 | 바뀌는 모습 |
|---|---|---|
| `AppFrame` | 배경에 파랑·초록 그라디언트 | 단색 paper 배경 |
| `AppTopBar` | 반투명 블러(유리 효과) | 단색 바탕과 아래쪽 구분선. sticky와 `/ feed` 경로 표시는 유지 |
| `BottomNavigation` | 선택된 항목을 채운 사각 블록으로 표시 | 단색 바탕과 위쪽 구분선. 선택 항목은 코발트 글자와 위쪽 표시선 |
| `TopBarActions` | 메뉴 패널이 유리 효과 | 단색 패널과 구분선 |
| `Modal` | 블러 배경, 큰 그림자 | 단색으로 어둡게 덮는 배경, 구분선 패널. 다크에서는 그림자 없음 |
| `Button` | 둥근 버튼 (10~12px) | 키캡 버튼. 주요 버튼은 코발트 키, 보조 버튼은 회색 키. 6px 라운드, 40px 높이. 마우스 올림·누름·비활성·포커스 상태를 모두 갖춤 |
| `IconButton` | 둥근 배경 | 키캡 또는 배경 없는 버튼 |
| `Card` | 큰 라운드(16px) 박스. 안쪽용 variant가 "카드 안 카드"를 만듦 | 8px 패널과 구분선, 대각선 두 모서리를 깎음(지원 브라우저만). 안쪽용 variant는 박스가 아니라 구분선으로 나눈 영역이 됨 |
| `ListRow` | 행마다 개별 박스 | 구분선으로 나뉜 행 |
| `Chip` | 알약 모양 | 모서리를 깎은 작은 태그, 또는 상태색 글자 |
| `IconBadge` | 원형 아이콘 배경 | 6px 라운드의 작은 사각 타일 |
| `StatCard` | 숫자마다 개별 카드 | 구분선 행 위에 큰 숫자(표 형식 숫자)와 라벨 |
| `SegmentedTabs` | 알약 모양 탭 | 오목한 트레이 안의 키 버튼, 선택된 것은 눌린 상태. `aria-selected` 추가 |
| `SectionHeader`, `PageIntroCard` | 제목 위 `feed / target` 경로 라벨 | 결정 필요 (아래) |
| `Icon` | svg에 `aria-hidden` 없음 (FAIL 22곳) | `aria-hidden` 추가 |
| `AppContent` | 화면 폭 768/560px | 그대로 |

## 진행 순서

1. 접근성 수정(`Icon`)
2. 컨트롤(`Button`, `IconButton`, `SegmentedTabs`)
3. 표면(`Card`, `ListRow`, `Chip`, `IconBadge`, `StatCard`)
4. 제목(`SectionHeader`, `PageIntroCard`)
5. 셸(`AppFrame`, `AppTopBar`, `BottomNavigation`, `TopBarActions`, `Modal`)
6. 검증: hallmark 정적 검사와 스크린샷 검사, 테스트 실행

## 테스트 영향

`tests/unit/shared/ui` 테스트는 정확한 클래스명을 많이 확인함(`h-10`, `rounded-[10px]`, `rounded-2xl`, `rounded-full`, `bg-surface`, `p-4`, `text-[11px]`, `shadow-2xl`, `bg-black/60` 등). 대략 14개 파일에서 30개 안팎의 확인 구문이 깨질 것으로 예상.

- **그대로 지키는 것**: 화면 폭(`max-w-[768px]`), 열 구성(`grid-cols-*`), 상태 의미(`bg-primary`, `text-accent-red`, `opacity-75`)는 컴포넌트에서 계속 유지해서 테스트를 안 깸.
- **목록으로 받는 것**: 그래도 깨지는 스타일 확인 구문은 바로 고치지 않음. 구현이 끝나면 "확인 구문 / 깨진 이유 / 수정안" 목록을 보여주고, 승인받은 것만 고침.

## 3단계에 미치는 영향

화면 쪽(`features/*`)에서 공용 컴포넌트에 직접 덧씌운 클래스(`rounded-2xl` 등)는 그대로라서, 2단계 직후엔 일부 화면이 어색하게 보일 수 있음. 그건 3단계에서 정리.

## 결정이 필요한 것

1. **경로형 라벨(`feed / target`, `platform / me`, `{로고} / welcome`) 처리**: hallmark는 제목 위 작은 라벨(eyebrow)을 금지함. 하지만 이 라벨도 원래 있던 내용이라 그냥 지울 수는 없음.
   - **가. 탑바 경로로 합치기 (추천)**: 탑바에 이미 `{로고} / feed` 경로가 있으니, 화면 안 라벨은 지우고 탑바 경로만 남김. 섹션 라벨(`feed / target`)은 제목만 남기고 지움. 깨지는 텍스트 확인 테스트는 승인 목록에 넣음.
   - **나. 유지**: 라벨을 남기되 hallmark 규칙에 맞게 본문 서체, 한 단계 작은 크기, 흐린 색으로 바꿈. 예외로 기록.
2. **단계별 커밋 여부**: 1단계 결과는 아직 커밋하지 않음. 2단계 시작 전에 1단계를 커밋할지.

# 경로형 라벨 처리 결정

> 추천사항으로 하자

## 답변

경로형 라벨은 **가안(탑바 경로로 합치기)**으로 확정.

## 적용 내용

- 화면 안 경로형 라벨(`{로고} / welcome`, `{로고} / feed` 등)은 지우고, 탑바의 `{로고} / feed` 경로만 남김.
- 섹션 라벨(`feed / target`, `platform / me` 등)은 지우고 제목만 남김.
- 라벨 텍스트를 확인하는 테스트가 깨지면 승인 목록에 넣어 함께 처리.
- 지운 라벨은 hallmark 규칙대로 handoff(작업 결과 보고)에 "dropped" 항목으로 기록.

## 남은 결정

- 단계별 커밋 여부. 2단계 시작 전에 1단계를 커밋할지.
